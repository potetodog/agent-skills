# QA項目書生成 (qa-sheet)

現在のブランチの差分から、レビュアーやQA担当者がそのまま使えるQA項目書を作る。ゴールは「漏れなく」より「そのPRで実際に壊れうる場所を突く」こと — 機械的に全観点を埋めるのではなく、diffの中身を読んで判断する。

`disable-model-invocation: true` を設定しているため、Claudeが自動判断で実行することはなく、`/qa-sheet` と明示的に呼び出したときだけ動く。

比較対象ブランチ(省略可): $ARGUMENTS

## 全体の流れ

1. **差分を取得する** — `scripts/get_diff.sh` を実行する。`$ARGUMENTS` で比較対象ブランチが指定されていればそれを渡す（例: `scripts/get_diff.sh develop`）。指定がなければ引数なしで実行し、`scripts/detect_base_branch.sh` がリポジトリのデフォルトブランチ（origin/HEADが指すブランチ。main/master/develop等）を自動検出する。

   出力には以下が含まれる:
   - 比較対象ブランチ・現在のブランチ・merge-baseコミット
   - 変更ファイル一覧（追加/変更/削除/リネームのstatus付き）
   - 差分全文を書き出した一時ファイルのパス

2. **差分を読んで理解する** — 一時ファイルをReadツールで開き、変更内容を読む。ファイル数が多い場合は、変更ファイル一覧を見て優先度の高いもの（ロジックの分岐、フォーム、金額/権限/認証まわり、UIコンポーネントなど）から読む。「このコードが何を変えたか」「その変更で新しく壊れうる場所はどこか」を自分の言葉で説明できるところまで理解してから次に進む。

3. **コードの外にある分岐を探す** — diffを構文的に読んでいるだけでは気づけない分岐が埋め込まれていないか確認する。詳細は「コードの外にある分岐」を参照。該当するものが見つかったら、値の定義元を実際に読んで取りうる値・組み合わせを正確に把握する。ここで把握した組み合わせは、次のステップで条件分岐網羅・エッジケースの項目として（間引かずに）反映する。

4. **QA観点ごとに項目を洗い出す** — 下記「QA観点の定義」を参照し、diffの内容に基づいて項目を作る。すべての観点を機械的に埋める必要はない。該当する変更がなければその観点は書かない（例: バックエンドのみの変更ならレイアウト観点は不要）。ステップ3で組み合わせを洗い出した場合は、それぞれの組み合わせを個別の項目にする。「権限ごとに確認する」のような、値を列挙しない曖昧な項目にしない。

5. **網羅性を自己チェックする** — TSVを書き出す前に、洗い出した分岐（構文的な分岐・ステップ3で見つけたコードの外の分岐の両方）について、想定される値・パターンの組み合わせがすべて項目化されているか数え上げて確認する。抜けが見つかったらここで追加する。手順を端折って次のステップに進まない。

6. **TSVファイルを直接書き出す** — 「出力フォーマット」の手順に従い、Writeツールでタブ区切りのTSVファイルを作成する。変換用のスクリプトは使わない（QA項目の作成自体がこのSkillの本体であり、機械的な変換ステップを挟む意味がないため）。

7. **プレビューを見せる** — 生成したTSVの内容を、チャット上ではMarkdownテーブルとして見せる（生のタブ区切りテキストはチャットでは読みにくいため）。あわせてTSVファイルのパスを伝える。

8. **貼り付けやすくする** — macOSであれば `pbcopy < <出力ファイル>` でクリップボードにコピーし、「スプレッドシートのセルを選択して Cmd+V で貼り付けられます」と伝える。SendUserFileツールが使えるならTSVファイルも送付する。

## コードの外にある分岐

`if`/`switch`/三項演算子のような構文的な分岐だけを見ていると、次のような「コードの外にある分岐」を見落とす。これらはビジネスルールとして実質的に分岐しているのに、diffを構文的に読むだけでは検出できない。

- LLMへのプロンプト/instructions（システムプロンプトなど自然文の指示）の中で、権限・ロール・プラン種別・言語などの値によって回答内容や振る舞いを出し分けている箇所
- enum・定数一覧・設定ファイルなど「取りうる値の一覧」を定義している箇所と、その値を参照して振る舞いを変えている箇所（例: 権限の種類、ステータスの種類、プランの種類）
- i18n/ロケールなど、外部の値によって出力内容が変わる箇所

これを毎回律儀に探しに行くと、関係のない差分にまで無理に適用して項目を水増ししてしまう。次のようなシグナルがdiffにあるときだけ、重点的に洗い出す（シグナルが無ければこのステップは軽く流してよい。あくまで例であり、同じ発想に当てはまる他のパターンにも判断を広げてよい）。

- 変更/追加されたファイル名・クラス名・関数名に、権限・ロール・区分・種別・設定を表す語（Permission, Role, Plan, Policy, Context, Flag, Config、または「権限」「区分」「種別」など）が含まれる
- LLMに渡す長い自然文の指示を返すメソッド・関数が変更されている（例: Agent/Prompt系クラスの `instructions()` のようなメソッド）
- 上記のような値の一覧を取得・参照している呼び出し元がある（例: `grantedPermissions()` のような取得・判定メソッドの呼び出し）

該当する場合は、値の意味を推測で済ませず、定義元（enum定義ファイル、定数一覧、設定ファイルなど）を実際に読む。取りうる値の組み合わせ（単独保持/複数保持/なし/未ログインなど、対象に応じた組み合わせ）を洗い出し、値の数×代表的な入力パターンのクロス表として条件分岐網羅・エッジケースの項目に反映する。

## QA観点の定義

それぞれの観点が「何のためにあるか」を理解した上で、diffに実際に当てはまるものだけを使う。

- **正常系** — その変更によって新しく成立する、または変化する主要なユースケースが、意図通りに動くか。「そもそもこの変更は何のためのものか」に対する一番素直な確認。
- **条件分岐網羅** — diff内に増えた/変わった `if`・`switch`・三項演算子・early return・フィーチャーフラグなどの構文的な分岐に加えて、「コードの外にある分岐」（LLM instructions内のビジネスルールやenum/設定値による振る舞いの出し分けなど。詳細は「全体の流れ」ステップ3を参照）も対象に、各パターンが期待通りの結果になるかを洗い出す。分岐が増えたのにテストが1パターンしか押さえていないと、そこが最初に壊れる。
- **デグレ** — この変更に隣接する既存機能、この関数の他の呼び出し元、共通化されたコンポーネント/ユーティリティを使っている他の画面など、「直接変更していないが影響を受けうる場所」が壊れていないか。diffだけを見ていると気づきにくいので、変更箇所の呼び出し元をコードベース内で軽く確認するとよい。
- **エッジケース** — 境界値（0件/最大件数、文字数の上限/下限）、空文字列・null・undefined、同時実行・連打、権限がない/セッション切れの状態など、「通常は起きないが起きたら困る」入力・状態。
- **レイアウト** — UIやスタイルに関わる変更（`.tsx` `.jsx` `.vue` `.svelte` `.css` `.scss` `.html` などUI関連ファイルの変更）がある場合のみ使う。レスポンシブ崩れ、長い文字列でのはみ出し、ダークモード、多言語（日本語/英語での文字数差）などを確認する。UIに無関係な変更ではこの観点自体を出力しない。

## 出力フォーマット

以下の5列のTSV（タブ区切り）で出力する。1行目はヘッダー行。事前知識のない確認担当者がこのファイルだけを渡されても迷わないよう、大項目→中項目→小項目の順で読めば「どの機能の、どういう観点の、何を確認するのか」が上から辿れるようにする。

| 列 | 内容 |
| --- | --- |
| 大項目 | 対象の機能・画面・モジュールのまとまり。diffの変更内容から意味のある単位を抽出する（例:「ログイン」「FAQ回答（権限による出し分け）」「決済」）。確認担当者が最初に「これはどこの話か」を把握するための列 |
| 中項目 | QA観点（正常系/条件分岐網羅/デグレ/エッジケース/レイアウト）。ひとつの大項目の中に複数の観点の項目が混在する場合に使う。大項目の中身が単一の観点だけで完結するなら省略してよく、その場合は大項目→小項目の2階層で出力する（列自体は残し、該当行を空欄にする） |
| 小項目 | 個別の確認項目。具体的な確認内容を1行で書く |
| 確認手順 | 実際に行う操作を順番に書く |
| 期待結果 | 確認手順を行った結果、何がどうなっていればよいか |

```
大項目	中項目	小項目	確認手順	期待結果
決済	正常系	クーポン適用条件を満たす注文でクーポンが適用される	1. 条件を満たす注文を作る 2. クーポンコードを入力する 3. 決済を確定する	クーポン分の割引が適用された金額で決済が完了する
決済	条件分岐網羅	クーポン適用条件を満たさない場合は割引されない	1. 条件を満たさない注文を作る 2. クーポンコードを入力する	エラーメッセージが表示され、割引は適用されない
FAQ回答（権限による出し分け）	条件分岐網羅	閲覧権限のみを保持するユーザーへの回答範囲	1. 閲覧権限のみを付与したユーザーでログインする 2. FAQに質問する	閲覧権限で許可された範囲内の回答のみが返り、他の権限が必要な情報は含まれない
FAQ回答（権限による出し分け）	条件分岐網羅	権限を一つも保持しないユーザーへの回答	1. 権限を一切付与していないユーザーでログインする 2. FAQに質問する	権限が必要な回答は行われず、一般公開範囲の回答またはその旨のメッセージが返る
```

書き出す際は次の点に注意する:

- 列の区切りは実際のタブ文字（`\t`）を使う。半角スペースや全角スペースで代用しない。
- セルの中に改行やタブが入ると列がずれるため、確認手順のステップは `1. ... 2. ... 3. ...` のように1セル内で数字付きの一続きの文にするか、` → ` で連結する。改行は使わない。
- ファイル名は `qa-sheet_<比較対象ブランチ>_<現在のブランチ>.tsv` のように、どのブランチ間の差分かがわかる名前にする（例: `qa-sheet_main_feature-checkout.tsv`）。
- 保存先は `~/Downloads/` をデフォルトにする。スプレッドシートに貼り付けて使う一時的な成果物であり、リポジトリの資産として残す性質のものではないため、生成物でリポジトリを汚さない。リポジトリの資産として残したいとユーザーから指定された場合だけ、指定されたパス（例: `docs/qa/` 配下）に保存する。

## 進め方の注意

- 差分が非常に大きい（多数のファイル、無関係な変更が混在しているなど）場合は、全部を機械的に処理しようとせず、変更の意図ごとにまとまりを見つけて優先順位をつける。ユーザーに「特に手厚く見てほしい範囲」を確認してもよい。
- diffのファイル一覧に `.test.` `.spec.` を含むテストファイルしか含まれない場合や、フォーマッタ差分・自動生成ファイルのみの変更の場合は、QA項目を無理に作らず、その旨をユーザーに伝える。
- 生成物はあくまでたたき台。項目数を稼ぐための水増しは避け、レビュアーが読んで「たしかにここは確認すべき」と思える項目に絞る。
- 「コードの外にある分岐」の洗い出しは、該当するシグナルがない一般的な差分にまで無理に適用しない。関係の薄い項目を水増しすると、かえって本当に重要な項目が埋もれる。

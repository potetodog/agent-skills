# QA項目書生成 (qa-sheet)

現在のブランチの差分から、レビュアーやQA担当者がそのまま使えるQA項目書を作る。ゴールは「漏れなく」より「そのPRで実際に壊れうる場所を突く」こと — 機械的に全観点を埋めるのではなく、diffの中身を読んで判断する。

`disable-model-invocation: true` を設定しているため、Claudeが自動判断で実行することはなく、`/qa-sheet` と明示的に呼び出したときだけ動く。

比較対象ブランチ(省略可): $ARGUMENTS

## 全体の流れ

1. **差分を取得する** — `scripts/get_diff.sh` を実行する。`$ARGUMENTS` で比較対象ブランチが指定されていればそれを渡す（例: `scripts/get_diff.sh develop`）。指定がなければ引数なしで実行し、`scripts/detect_base_branch.sh` がリポジトリのデフォルトブランチ（origin/HEADが指すブランチ。main/master/develop等）を自動検出する。

   出力には以下が含まれる:
   - 比較対象ブランチ・現在のブランチ・merge-baseコミット
   - 変更ファイル一覧（追加/変更/削除/リネームのstatus付き）
   - 差分全文を書き出した一時ファイルのパス

2. **差分を読んで理解する** — 一時ファイルをReadツールで開き、変更内容を読む。ファイル数が多い場合は、変更ファイル一覧を見て優先度の高いもの（ロジックの分岐、フォーム、金額/権限/認証まわり、UIコンポーネントなど）から読む。「このコードが何を変えたか」「その変更で新しく壊れうる場所はどこか」を自分の言葉で説明できるところまで理解してから次に進む。

3. **QA観点ごとに項目を洗い出す** — 下記「QA観点の定義」を参照し、diffの内容に基づいて項目を作る。すべての観点を機械的に埋める必要はない。該当する変更がなければその観点は書かない（例: バックエンドのみの変更ならレイアウト観点は不要）。

4. **TSVファイルを直接書き出す** — 「出力フォーマット」の手順に従い、Writeツールでタブ区切りのTSVファイルを作成する。変換用のスクリプトは使わない（QA項目の作成自体がこのSkillの本体であり、機械的な変換ステップを挟む意味がないため）。

5. **プレビューを見せる** — 生成したTSVの内容を、チャット上ではMarkdownテーブルとして見せる（生のタブ区切りテキストはチャットでは読みにくいため）。あわせてTSVファイルのパスを伝える。

6. **貼り付けやすくする** — macOSであれば `pbcopy < <出力ファイル>` でクリップボードにコピーし、「スプレッドシートのセルを選択して Cmd+V で貼り付けられます」と伝える。SendUserFileツールが使えるならTSVファイルも送付する。

## QA観点の定義

それぞれの観点が「何のためにあるか」を理解した上で、diffに実際に当てはまるものだけを使う。

- **正常系** — その変更によって新しく成立する、または変化する主要なユースケースが、意図通りに動くか。「そもそもこの変更は何のためのものか」に対する一番素直な確認。
- **条件分岐網羅** — diff内に増えた/変わった `if`・`switch`・三項演算子・early return・フィーチャーフラグなどの分岐を洗い出し、各分岐パターンが期待通りの結果になるか。分岐が増えたのにテストが1パターンしか押さえていないと、そこが最初に壊れる。
- **デグレ** — この変更に隣接する既存機能、この関数の他の呼び出し元、共通化されたコンポーネント/ユーティリティを使っている他の画面など、「直接変更していないが影響を受けうる場所」が壊れていないか。diffだけを見ていると気づきにくいので、変更箇所の呼び出し元をコードベース内で軽く確認するとよい。
- **エッジケース** — 境界値（0件/最大件数、文字数の上限/下限）、空文字列・null・undefined、同時実行・連打、権限がない/セッション切れの状態など、「通常は起きないが起きたら困る」入力・状態。
- **レイアウト** — UIやスタイルに関わる変更（`.tsx` `.jsx` `.vue` `.svelte` `.css` `.scss` `.html` などUI関連ファイルの変更）がある場合のみ使う。レスポンシブ崩れ、長い文字列でのはみ出し、ダークモード、多言語（日本語/英語での文字数差）などを確認する。UIに無関係な変更ではこの観点自体を出力しない。

## 出力フォーマット

以下の4列のTSV（タブ区切り）で出力する。1行目はヘッダー行。

```
分類	項目	確認手順	期待結果
正常系	○○フォームに必須項目を入力して保存できる	1. ○○画面を開く 2. 必須項目を入力する 3. 保存ボタンを押す	保存に成功し、一覧に反映される
条件分岐網羅	クーポン適用条件を満たさない場合は割引されない	1. 条件を満たさない注文を作る 2. クーポンコードを入力する	エラーメッセージが表示され、割引は適用されない
```

書き出す際は次の点に注意する:

- 列の区切りは実際のタブ文字（`\t`）を使う。半角スペースや全角スペースで代用しない。
- セルの中に改行やタブが入ると列がずれるため、確認手順のステップは `1. ... 2. ... 3. ...` のように1セル内で数字付きの一続きの文にするか、` → ` で連結する。改行は使わない。
- ファイル名は `qa-sheet_<比較対象ブランチ>_<現在のブランチ>.tsv` のように、どのブランチ間の差分かがわかる名前にする（例: `qa-sheet_main_feature-checkout.tsv`）。
- 保存先は `~/Downloads/` をデフォルトにする。スプレッドシートに貼り付けて使う一時的な成果物であり、リポジトリの資産として残す性質のものではないため、生成物でリポジトリを汚さない。リポジトリの資産として残したいとユーザーから指定された場合だけ、指定されたパス（例: `docs/qa/` 配下）に保存する。

## 進め方の注意

- 差分が非常に大きい（多数のファイル、無関係な変更が混在しているなど）場合は、全部を機械的に処理しようとせず、変更の意図ごとにまとまりを見つけて優先順位をつける。ユーザーに「特に手厚く見てほしい範囲」を確認してもよい。
- diffのファイル一覧に `.test.` `.spec.` を含むテストファイルしか含まれない場合や、フォーマッタ差分・自動生成ファイルのみの変更の場合は、QA項目を無理に作らず、その旨をユーザーに伝える。
- 生成物はあくまでたたき台。項目数を稼ぐための水増しは避け、レビュアーが読んで「たしかにここは確認すべき」と思える項目に絞る。

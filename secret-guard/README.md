# secret-guard

APIキー・アクセスキーなどのシークレットが、AIのツール実行（ファイル読み込み・シェル・外部通信）を経由して流出するのを検知・ブロックする PreToolUse フックと、そのセットアップ用スキル。

## 設計方針

**検知の主体はスキルではなくフック。** SKILL.md はモデルが読む指示文にすぎず、プロンプトインジェクション等でモデル自体が汚染されるシナリオでは防御にならない。フックはハーネスが全ツール呼び出しで決定論的に実行するため、モデルの状態に依存しない。

**「出ていく時」より「入ってくる時」に守る。** シークレットは一度コンテキストに入ると base64 や分割などで変形して持ち出せるため、出口の正規表現マッチは原理的に回避可能。そこで防御を二層に分けている:

| 層 | 対象 | 判定 |
| --- | --- | --- |
| 読み込みブロック | `.env`, `~/.aws/credentials`, `~/.ssh/id_*`, `.netrc` などの保護対象パスに触れるツール呼び出し | deny（拒否） |
| 出口検知 | Bash / WebFetch / Write などの引数に含まれる既知のAPIキー形式（AWS, GitHub, Anthropic, OpenAI, Slack, Stripe, 秘密鍵ブロック, JWT 等） | ask（ユーザー確認） |

その他の設計判断:

- **依存は bash + jq + grep のみ。** npm install や外部スキャナ（gitleaks 等）に依存しない。jq が無い環境では fail-closed（exit 2 で全ブロック）に倒し、防御が静かに無効化されるのを防ぐ
- **検知理由にマッチした値を含めない。** フック出力やログが第二の流出経路になるため、パターン名のみ報告する
- **パターンはコードから分離。** `scripts/patterns.json` を編集するだけで保護パス・検知パターン・allowlist（`.env.example` やプレースホルダキーの誤検知対策）を調整できる

## 構成

```
secret-guard/
├── SKILL.md              # セットアップ・診断・調整の入口（/secret-guard で呼び出す）
├── hooks.example.json    # settings.json にマージするフック設定 + permissions.deny のスニペット
└── scripts/
    ├── guard.sh          # PreToolUse フック本体
    ├── patterns.json     # 保護パス・検知パターン・allowlist の定義
    └── self_test.sh      # 代表ペイロードでの動作確認
```

## インストール

スキルをインストール後、Claude Code で `/secret-guard install` を実行すると、対話でフックのセットアップまで行える。手動で設定する場合は `hooks.example.json` の内容を `~/.claude/settings.json`（またはプロジェクトの `.claude/settings.json`）にマージし、`command` を `guard.sh` の絶対パスに書き換える。

動作確認:

```bash
scripts/self_test.sh
```

## 限界

- 出口検知はパターンベースであり、変形されたシークレットや未知の形式は検知できない。層1の読み込みブロックとネットワーク側の制限（サンドボックス・ドメイン許可リスト）との併用が前提
- 保護ファイルを名指ししない読み出し（親ディレクトリ全体への Grep など）は層1では検知できない。`permissions.deny` とサンドボックスが後ろ盾
- シークレットが一度コンテキストに入るとセッションのトランスクリプトファイルにも平文で残る。これも読み込み時点でブロックする理由のひとつ
- フックが検査するのはツール呼び出しの入力のみ。モデルの応答テキスト自体は対象外

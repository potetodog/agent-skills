チームメンバーに何かを説明するための、**自己完結した1ファイルのHTML**を作る。

対象: $ARGUMENTS

## これは何のためのコマンドか

仕様書とは限らない。想定する用途は次のどれか。

- この会話でまとまった検討結果を、他のメンバーに共有する
- ソースコードの処理内容を、実装を追わなくても分かる形にする
- 仕様・設計を、全員が同じ理解になるよう配る

いずれも共通するのは「**読み手はこの会話にいなかった**」こと。前提の共有から始める。

## 素材

- `.claude/templates/explain-html/template.html` — CSS込みの骨格。**CSSは1文字も変えずに丸ごとコピーする**
- `.claude/templates/explain-html/components.md` — 部品カタログとSVG作図の約束事

最初にこの2つを読む。CSSを自作しない。カタログにない見た目を作らない。

## 手順

### 1. 何を・誰に、を決める

引数がなければ**この会話の内容**が対象。あれば対象のファイルやコードを読む。

次の3つが自分の中で埋まらなければ、**まとめて1回だけ**聞く。埋まるなら聞かずに進む。

| 決めること | 判断のしかた |
| --- | --- |
| 読み手 | 会話の文脈から分かることが多い。分からなければ聞く |
| 前提知識 | 読み手が既に知っていることは書かない。ここを間違えると分量が倍になる |
| 出力先 | リポジトリの資産なら `docs/<主題のスラッグ>/`、その場限りの共有ならスクラッチパッド |

### 2. 骨格を決める

**ここが一番重要**。テンプレートの章立てをそのまま使わない。内容から決める。

文書タイプ別の出発点（あくまで叩き台。合わなければ変える）:

- **処理・ロジックの説明** — 全体像 → 入力 → 各工程 → 出力 → 通し例 → 値の一覧
- **設計・提案** — 何を解こうとしているか → 現状 → 案 → 選んだ理由 → 決まっていないこと
- **コード解説** — 責務 → 呼ばれ方 → 主要な分岐 → 落とし穴 → 変更するときの注意
- **検討結果の共有** — 結論 → そう決めた理由 → 検討した別案 → 次にやること

骨格を決めるときのチェック:

- **章は4〜10。** それ以上は分割しすぎ、それ以下は1章が長すぎる
- **目次を並列にしない。** 章が6を超えたら `toc__group` で束ねる。読み手が「本題はどこからどこまでか」を目次だけで分かる状態にする
- **各章に「これは何のための章か」が1文で言えるか**を確認する。言えない章は消す
- 用語辞典・要約・改訂履歴は、**必要だと判断した場合だけ**足す。惰性で付けない

### 3. 書く

`components.md` の「書き方のルール」に従う。特に外せないもの:

- **略号を使わない。** 元資料に `Z` `L1` `x軸` があっても、その場で意味の分かる日本語に置き換える
- **具体値を入れる。** 「しきい値以上なら」ではなく「8.4以上なら」。抽象論より数字1つ
- **図は分岐・順序・比較のあるところに入れる。** 箇条書きで足りるものを図にしない
- **1章に図は1〜2枚**、SVGの `marker id` は図ごとに別名
- **段落は4文まで。** 超えるなら文の切れ目で `<br>` を入れるか段落を割る
- 人名（田中さんなど）を出さない。「ケースA」「ある社員」にする
- 未確定事項は、確定として書けるならそう書く。書けないなら `note--warn` で1箇所にまとめる

決めきれない値やロジックの矛盾に気づいたら、**黙って辻褄を合わせない**。
自分の判断で埋めた箇所は、最後にユーザーへ「ここは自分が決めた」と申告する。

### 4. 検証する

書き終えたら必ず全部走らせる。目視で済ませない。

```bash
F=<出力したHTMLのパス>

# タグの対応
for t in div table tr td p main figure svg; do
  echo "$t: $(grep -o "<${t}[ >]" "$F" | wc -l) / $(grep -o "</${t}>" "$F" | wc -l)"
done

# 目次のリンク切れ（出力が空なら正常）
grep -o 'href="#[^"]*"' "$F" | sed 's/href="#\(.*\)"/\1/' | sort -u > /tmp/eh-href.txt
grep -o 'id="[^"]*"' "$F" | sed 's/id="\(.*\)"/\1/' | sort -u > /tmp/eh-id.txt
comm -23 /tmp/eh-href.txt /tmp/eh-id.txt

# SVGのmarker id重複（出力が空なら正常）
grep -o '<marker id="[^"]*"' "$F" | sort | uniq -d

# 外部リクエストの混入（出力が空なら正常。自己完結が絶対条件）
grep -oE '(src|href)="https?://[^"]*"' "$F" | grep -v '^href="#'
```

JavaScript を入れた場合は `node --check` も通す。ただし**動くものを埋め込むのは原則不要**。
本文で説明できることをインタラクションに逃がさない。

### 5. 渡す

`SendUserFile` で `display: "render"` を付けて送る。
あわせて、**骨格をどう決めたか**と、**自分の判断で埋めた箇所**を本文で報告する。

## デザインの制約（変えない）

- **色は青・グレー・赤のみ。** 赤は警告専用。緑・黄・紫を足さない。強さは青の濃淡（`lv0`〜`lv3`）で表す
- **ダークモード非対応。** `prefers-color-scheme` を書かない
- **影を使わない。** 階層は罫線と背景色の差で表す
- **フォントは游ゴシック、ウェイトは500と700のみ**
- **外部リソースゼロ。** CDN・Webフォント・画像URLを参照しない。図はインラインSVG

## やらないこと

- インタラクティブなシミュレーターやデモの埋め込み（個別に依頼されたときだけ）
- ディレクトリ構成の章（コード解説で本当に必要なときだけ、`tree-tbl` で）
- 全文シンタックスハイライト（説明したい行だけ `.k` `.c` `.hl` で着色）
- Markdown版の同時生成（頼まれたときだけ）
